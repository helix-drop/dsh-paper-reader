# 来源映射完善与处理流程审查

2026-10-15。本次完善阅读插件的装配、翻译、导入、阅读和发布流程，并审查实际调用链。检查对象包括插件代码、当前独立工作区的 Python 运行时及 LinguaGacha Markdown V2 解析源码。未执行收费转写或翻译，未向 Obsidian 发布，未重写已有文献正文或转写预算。

| 本次结果 | 实现 |
|---|---|
| 装配来源 | 新增 runtime/assemble_with_provenance.py，仍调用既有装配器；在内存中记录正文和注释的渲染边界，保留跨页 pid_chain，最终 Markdown 与未修改装配器逐字节比较 |
| 段落映射 | 每份 PDF 装配原文生成同名 .source-map.json；包括稳定段落标识、Markdown 块指纹、源段落标识、逻辑页、原 PDF 页集合与连续范围、裁切区域、原 PDF / 规范化底本 / 配置 / 装配证据指纹 |
| 无源内容 | 自动生成的书名、导航目录和分隔线保留生成标识与未映射原因，不编造页码；缺少来源页的注释单独标明未定位 |
| 翻译关联 | 原文快照旁保存段落清单，翻译输入携带段落标识；CLI 和 HTTP 输出均核对标识数量、唯一性、顺序、段落结构、脚注及附件，再清除工作标记并保存译文映射 |
| 版本失效 | Markdown 或原 PDF 指纹不同、段落标识缺失或重复、译文改写来源页时停止自动关联；存在失效映射时不降回文字猜测 |
| 阅读 | 优先读取已验证来源映射；跨页段落定位起始页，同时保留完整页集合与范围；历史无映射文献继续采用既有保守匹配，不声称已经补齐 |
| 导入 | 原文和译文来源映射分别导入；PDF 路径限制在阅读工作区或发布目录。上传文件改名后，可选择已登记的原 PDF，摘要一致才重新关联；译文必须保留当前原文的标识、指纹和全部来源页信息 |
| 导出 | 有有效映射的阅读视图提供下载来源映射；Markdown 与映射须配套保存，单独的 Markdown 不包含完整来源信息 |
| 发布 | 有原文来源映射时，原文、译文和双语 Markdown 各自生成配套映射；附件路径改变后重算 Markdown 指纹。清单同时包含原始PDF.pdf 和规范化后的阅读底本.pdf，映射只指向原始PDF.pdf，且采用相对路径 |

来源映射属于用户本次明确要求保留的必要阅读附件，随成品保留。逐页 JSON、预算、处理日志和中间 provenance 记录继续留在项目内，不进入 Vault。双语 Markdown 的两个语言块共享源段落来源，各展示块另有唯一标识。程序关联只能证明数据来源和结构对应，不能证明译文语义正确。

## 审查发现及处置

| 优先级 | 原问题与实际影响 | 本次处置 |
|---|---|---|
| P1 | 跨页合并只在内存保留源段落关系，Markdown 不能稳定追溯原页 | 装配时记录真实渲染边界与源段落链，生成映射并校验上游文件摘要；不按短句在章节中搜索来源 |
| P1 | 译文原先主要按块数量与顺序配对，同样数量仍可能错配 | 引入显式段落标识；不接受丢失、重复和换序的标识，不按位置补造译文来源；旧无标识译文可保留，但不能凭结构检查获得新映射 |
| P1 | 一个并发章节失败会使 Promise.all 提前返回，其他章节仍可写入 | 等待所有已启动章节结束后再结束任务；后续可依照原状态与预算续跑 |
| P1 | 发布只需译文结构校验，审校文件存在也不能证明审校对应当前版本 | 发布须登记当前版本审校；报告必须携带原文和译文指纹，登记后再校验报告自身指纹。导入新译文会清除旧审校与发布状态 |
| P1 | 已开始转写后仍可更换章节编号或范围，可能形成新的章节预算目录 | 已尝试转写或存在审计记录时锁定章节；拒绝越界、重叠、非整数页码、不安全及重复编号；底本锁定后不再重做输入检查 |
| P1 | 术语整理额外调用分析模型，即使 DSH 已经提供候选；--force 可覆盖人工术语表 | 首次审查移除隐藏调用；后续按用户明确要求改为全部文档必须执行 LinguaGacha 全文分析、清洗和原文冲突处理，详见 [术语流程](GLOSSARY-WORKFLOW.md)。旧文件不再单独满足翻译条件，历史版本仍保存 |
| P2 | 文字层分支没有调用其专用结构检查 | verify 阶段增加 verify_textlayer_structure.py，继续执行逐页检查。3c 要求章 Markdown 已存在，保留在装配后执行，避免制造前置依赖循环 |
| P2 | 发布只带规范化底本，原文件页序与裁切区域无法完整恢复 | 同时保留原始 PDF 和规范化底本，来源映射指向原始 PDF |
| P2 | 图片检查只覆盖部分 Markdown 写法，译文目录不一定持有原文相对图片副本 | 纳入 HTML 图片、Obsidian 图片及 URL 编码路径；译文同名相对附件可从已核对的原文目录取回，再生成相对附件清单 |
| P2 | 审校预设要求加载 book-translation-review，但读取守卫不允许该规则目录 | 只开放该目录下的 Markdown 规则，其他凭证、正文、预算和写入限制保持；守卫版本更新为 2026-10-15.1 |
| P2 | 整书标题默认采用任务目录名 document，导致导出的首标题错误 | 沿用既有输出路径，生成首标题时使用已确认书名，不修改转写章节正文 |
| P2 | 文档与界面声称原生 PDF 默认直接提取、3c 在装配前执行、verify_output 支持不存在的参数 | 对照实际实现更新说明；原生 PDF 仍按用户所选视觉或文字层方式执行 |

全书装配继续使用原装配器的章节完整性、顺序和脚注命名空间处理，补充拼接后脚注定义检查。audit_book.py 实际只检查整书 Markdown 存在且非空，不把它描述为全文内容验收。装配来源记录递归核验章节及页 JSON 的摘要，文件改变后须重新检查和装配。

## 验证与边界

| 验证 | 结果 |
|---|---|
| 自动测试 | 17 项通过，覆盖迁移路径、附件访问、定位、跨页与重复段落、显式译文配对、指纹失效、可移植发布、旧审校、术语及预算锁定、并发失败收尾 |
| 真实转写样本 | 在 Landron 论文的临时副本上运行既有章节装配器及新增记录器；225 个渲染块来源记录，章节 Markdown 与现有正式章节字节一致 |
| 整书拼接入口 | 同一临时样本经整书入口生成 230 个展示块，其中 225 个具有 PDF 页码，另 5 个为新增书名、目录与分隔内容；10 个块跨页，原文件页序为 3—21 |
| 翻译路径 | 使用离线 CLI 替身检查实际准备、输出采纳、映射生成、重复成功复用和导入失效流程；未发送真实翻译请求 |
| 发布路径 | 在临时目录实际发布并重新读取原文、译文、双语映射及原始 PDF；未写入实际 Vault |
| 既有数据 | 禁止读取旧 K-PdfToMd 与旧 papers 的沙箱复查通过：43 条任务、20 篇文献、20 处正文图片可读，书签与整理状态不变 |
| 正式宿主 | 重启后处理面板正常，来源映射导入和对应原 PDF 选择控件可见；未在正式库上传测试文件或启动模型 |
| 预算 | 24 份现有 attempts 摘要保持一致，无模型调用 |

新流程适用于后续装配与翻译。已有 20 篇文献未批量重写或重新翻译，原有定位覆盖率不会因增加代码自动变为全文覆盖。旧 PDF 任务可重新执行原文校验与确定性装配以生成来源映射，随后须导入有可靠段落标识的译文映射，或按新输入重新翻译；旧翻译缓存和原译文保留。没有映射的外部 Markdown 仍可阅读，但不能凭文件名或段落顺序推导原 PDF 页码。

尚未验证真实模型是否始终保留工作标记；若服务或模型移除标记，新流程会拒绝自动采纳并保留原始输出，不追加隐藏请求。扫描内容是否逐字准确、否定和术语是否译对、脚注是否语义错接，仍需源页与独立审校证据。当前没有认定任何现有整书已经重新完成语义验收。

## 接口与产物约定

| 入口或产物 | 约定 |
|---|---|
| Markdown 配套文件 | 完整文件名后追加 .source-map.json，例如 original.md.source-map.json |
| 装配中间记录 | .provenance.json，留在工作区，保留输入文件摘要及渲染段落边界 |
| 翻译输入 | translation-input/original.md、原文映射、source.md、block-manifest.json；source.md 含工作标记，不作为阅读成品 |
| 翻译输出 | translation/translated.md、配套来源映射、alignment.json；原始 CLI 输出继续留在 runs 目录 |
| 来源映射导入 | POST /pipeline/tasks/:id/source-map?view=original 或 translation；可用 pdfSourceId 指定已登记且摘要相同的 PDF |
| 来源映射下载 | GET /pipeline/tasks/:id/source-map?view=original 或 translation |
| 审校报告 | review/report.md 须包含当前版本的 dsh-review-source 和 dsh-review-target HTML 注释标记；面板会在审校任务中提供对应指纹 |

实际 HTTP 前缀为 /api/paper-reader。来源映射独立于 Markdown 排版，不向阅读正文写入工程标识。发布仍需用户在面板确认具体成品清单，不因完成映射或程序检查而自动发布。
